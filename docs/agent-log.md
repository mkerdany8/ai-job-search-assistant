## Iteration 2

Prompt given:
Build it. Fill in this log as you go. Persist results to
data/applications/<slug>.json. Document the RDAP and whois dependencies in
the README. Keep what you reasonably can reproducible. Do not run the two
test postings.

What it produced:
src/whois_lookup.py, src/legitimacy.py, src/fit.py, src/advice.py,
src/report.py, advise.py, README.md. No existing module was modified.

What I had to fix:
Six defects, all found by testing before the first full run.

1. seed_domains missed bare hostnames. `www.acme.com` with no scheme matched
   neither the URL nor the email regex. Added a bare-domain pattern with a
   TLD allowlist, so `Node.js` and `index.html` do not come back as domains.

2. Real posting PDFs contain no URLs at all. Checked three: the browser print
   keeps links outside the text layer, so seed domains are empty in practice.
   The mechanism still matters for a scam posting sent as a PDF, so it stays,
   but the prompt now states that an empty list means nothing was extractable
   and is not a warning sign, and tells the agent to search for the official
   domain instead.

3. The skill matcher was too literal. `RESTful APIs` scored as missing against
   a resume listing `REST APIs`. Replaced substring matching with token
   matching: stopwords dropped, plurals folded, and prefix stemming capped at
   3 characters. The cap is what keeps `java` from matching `javascript`,
   which would inflate the score. Verified against both lists of cases.

4. `CI/CD pipelines` still scored as missing against a resume listing `CI/CD`,
   because the extra token was uncovered. Added reverse coverage, restricted
   to resume terms of two or more tokens. Without that restriction `Java`
   matches `Java Spring Boot`, which is a different requirement.

5. The implied-match tier never fired. `_norm` keeps `.` on purpose for `.NET`
   and `Node.js`, which left sentence-final periods stuck to prose tokens, so
   `api.` never matched `api`. Now strips trailing dots only.

6. whois parsing was wrong in two ways, both serious.
   - A nonexistent `.com` was reported as registered since 1985-01-01. The
     macOS whois client returns the IANA record for the TLD when a domain does
     not exist, and 1985-01-01 is when `.com` itself was created. A domain
     that does not exist is the strongest fraud signal there is, and it was
     being reported as the opposite. The parser now only reads the block
     naming the queried domain, and treats a bare IANA referral as
     unregistered.
   - `Registrant Organization:` with an empty value returned the next line's
     street address. `\s*` around the colon matches newlines, so the match ran
     past the end of the empty field. Changed to `[ \t]*`.

Also found: rdap.org returns 403 to the default python-requests user agent
because of Cloudflare. Sending our own user agent returns 200. Without this
RDAP never answered and every lookup silently fell through to whois.

Verified before handover: whois correct on rbc.com, td.com, seneca.ca and two
nonexistent domains; full pipeline run on postings/software-developer-rbc.pdf
(green verdict, 53% fit); HTML well-formed, self-contained, sections in order,
escaping holds. The two test postings were left unrun.

## Iteration 3

Prompt given:
Extraction over-extracts. The TD posting returned 17 required skills including
"coding", "debugging", "unit testing", "software delivery practices" and
"infrastructure", exploding one bullet into five entries. This inflates the
fit-scoring denominator. Filter generics in fit.py rather than tightening
schema.py, so data/jobs stays a faithful record, the judgement sits in one
visible place, and the committed market and gap analyses stay valid. Log what
was filtered.

What it produced:
A generic-activity filter in src/fit.py, applied before coverage is computed.
Two lists: generic activities to drop, and named practices that survive
despite containing a generic word. Filtered entries are logged at debug level,
stored on SkillOverlap, passed to the scoring model as excluded context, and
listed in the HTML report under the skill chips. schema.py untouched. Plus the
README re-extraction note.

What I had to fix:
Nothing new broke. Two design notes worth recording.

First, extraction granularity is unstable run to run, not merely too coarse.
The same TD PDF yielded 17 required skills on one run and 7 on another, a 2.4x
swing in the denominator. Final scores were 40 / 39 / 40, all in the same
band. The fixed threshold table absorbed the swing, which is evidence for
keeping the band mapping out of the model, but it is not something to rely on
within a point or two of a boundary.

Second, filtering removes generic entries from the numerator as well as the
denominator, so it can move a score down. On software-developer-bmo the two
matched requirements were "Programming" and "System and Technology
Integration", both generic, so required-skills coverage went from 25% to 0%
over the two named requirements that remain. That is the honest reading —
matching the word "Programming" was never evidence of fit — but it is a real
consequence, not a free improvement.
